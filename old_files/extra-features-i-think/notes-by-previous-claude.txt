# Comprehensive Conceptual Summary: CHIM Cache Connector Enhancement

## **The Core Problem**

The CHIM JSON connector was experiencing **response quality degradation** compared to simpler connectors. Two primary theories:
1. **Strict JSON format requirements** forcing the LLM to prioritize structure over content quality
2. **Information overload** from extensive action lists and detailed response templates

Additionally, the caching system needed finer control over which messages remain dynamic vs cached.

---

## **Design Philosophy**

**Flexibility Without Breaking Compatibility:**
- All new features are opt-in with sensible defaults
- Existing configurations continue working unchanged
- Users can gradually adopt features as needed

**Reduce Cognitive Load:**
- Give users control over what information is sent to the LLM
- Allow "lightweight" modes that remove unnecessary complexity
- Let LLMs respond more naturally when appropriate

**Maintain Functionality:**
- Even when features are disabled, the connector should still work
- Default behaviors should be intelligent (e.g., defaulting target to speaker)
- Parser should handle both strict and loose formats

---

## **Feature Set: Detailed Breakdown**

### **1. Cache Control Enhancement**

**Feature: `dialogue_cache_uncached_count`**

**Purpose:** Control the boundary between cached and dynamic messages

**How It Works:**
```
Total messages: 59
dialogue_cache_uncached_count: 4

Message flow:
├─ Messages 1-55 [CACHED BLOCK] ← Cache control marker at end of message 55
└─ Messages 56-59 [ALWAYS DYNAMIC] ← Last 4 messages never cached
```

**Key Concepts:**
- Works with `max_dialogue_cache_context_size` (total size before cache reset)
- Two different mechanisms:
  - **max_dialogue_cache_context_size**: "When cache gets this big, clear it entirely and start over"
  - **dialogue_cache_uncached_count**: "When rebuilding cache, always leave last N messages out of the cache block"
- Placement calculation: `cache_control_index = total_messages - dialogue_cache_uncached_count - offset`

**Why This Matters:**
- Recent context is most important for maintaining conversation flow
- Keeping recent messages dynamic ensures they're always "fresh" to the LLM
- Allows balance between cache efficiency and response relevance

---

### **2. Response Format Flexibility**

**Feature: `response_format` ("json" | "simple")**

**Purpose:** Allow LLM to respond in natural format instead of strict JSON

**Two Modes:**

**JSON Mode (Default):**
- Full structured response with JSON template
- Strict format enforcement: "Use ONLY this JSON object"
- All fields explicitly defined in template
- Higher cognitive load but more predictable parsing

**Simple Mode:**
- Parenthetical format: `(mood)(listener)(action)(target) message`
- Natural language instruction instead of strict template
- Only includes enabled fields
- Example with all fields: `(happy)(Lydia)(Give)(health potion) Here, take this potion!`
- Example with actions disabled: `(happy) I'm glad to see you!`

**Implementation Concept:**
```
IF response_format == "json":
    - Include JSON template in system prompt
    - Demand strict JSON adherence
    - Parse using existing JSON extraction logic
    
ELSE IF response_format == "simple":
    - Build dynamic format string based on enabled features
    - Use natural language instruction
    - Parse using parenthetical pattern matching
    - Extract groups by position, map to appropriate fields
```

**Parsing Logic for Simple Format:**
1. Look for pattern at buffer start: `(text)(text)(text)`
2. Extract parenthetical groups based on what's enabled
3. Map by position and configuration to mood/listener/action/target
4. Everything after last `)` becomes the dialogue message
5. Set same global variables as JSON path would

---

### **3. Granular Content Control**

**Purpose:** Let users selectively disable parts of the prompt/response that may cause quality issues

#### **3a. `include_actions_list` (Boolean)**

**What It Controls:**
- **ON**: Full actions list sent in prompt, LLM must specify actions
- **OFF**: No actions list sent, action defaults to "Talk", target auto-disabled

**System Prompt Changes:**
```
WITH actions (ON):
System prompt includes:
- Full list of available actions (Give, Take, Attack, Follow, etc.)
- Response format requires action field
- Response format requires target field

WITHOUT actions (OFF):
System prompt includes:
- No actions list
- Response format omits action field
- Response format omits target field
- Connector defaults: action="Talk", target=last_speaker
```

**Why This Helps:**
- Action lists can be 20+ entries with descriptions
- Reduces token count significantly
- Removes decision paralysis for simple conversations
- LLM can focus on quality dialogue instead of action selection

#### **3b. `include_mood_requirement` (Boolean)**

**What It Controls:**
- **ON**: Mood/emotion field included in response format
- **OFF**: Mood field omitted, mood globals receive empty values

**Impact on Both Formats:**
- JSON: `{mood, action, target, message}` becomes `{action, target, message}`
- Simple: `(mood)(action)(target) message` becomes `(action)(target) message`

**Processing:**
- When disabled, `$GLOBALS["SCRIPTLINE_ANIMATION"]` and `$GLOBALS["SCRIPTLINE_EXPRESSION"]` get defaults
- Skyrim animation system handles empty mood gracefully

#### **3c. `include_target_requirement` (Boolean)**

**What It Controls:**
- **ON**: Target field required in response
- **OFF**: Target defaults to last user message speaker

**Dependency:**
- **Automatically enabled when `include_actions_list` is true**
- Can only be disabled when actions are also disabled
- Reasoning: Actions need targets, but "Talk" doesn't necessarily

**Default Behavior:**
```php
$defaultTarget = getLastUserMessageSpeaker($contextData);
// Searches context backwards for "SpeakerName: message" pattern
// Falls back to "Player" if not found
```

#### **3d. `include_listener_requirement` (Boolean)**

**What It Controls:**
- **ON**: Listener field required (who NPC is speaking to)
- **OFF**: Listener defaults to last user message speaker

**Purpose:**
- Some conversations have obvious listener (player in solo talk)
- Reducing fields = reducing cognitive load
- Still available for group conversations when needed

## **Architecture & Flow Changes**

### **New Helper Functions**

**1. `getLastUserMessageSpeaker($contextData)`**
- Searches context history backwards
- Looks for "Name: message" pattern in user messages
- Extracts speaker name
- Returns "Player" as fallback
- Used for defaulting target and listener

**2. `buildSimpleFormatInstruction($includeMood, $includeListener, $includeActions, $includeTarget)`**
- Dynamically builds format string based on configuration
- Examples:
  - All enabled: `(mood)(listener)(action)(target) message`
  - Actions disabled: `(mood)(listener) message`
  - Mood disabled: `(listener)(action)(target) message`
  - Only message: `message` (though parentheses might still be used)

### **Modified Sections**

**1. Configuration Loading (request() method start)**
- Read all new config options with defaults
- Store in instance variables for later use
- Validate dependencies (e.g., target auto-enabled with actions)

**2. System Prompt Construction**
- **JSON mode**: Include/exclude actions list, modify JSON template based on toggles
- **Simple mode**: Use `buildSimpleFormatInstruction()` to create dynamic format string
- Replace "Use ONLY this JSON" with natural language instruction in simple mode

**3. Cache Control Placement**
- Calculate: `lastIndex = count($completeEventList) - (3 + $addToIndex)`
- Apply `dialogue_cache_uncached_count`:
  - Standard: `$lastIndex = lastIndex - dialogue_cache_uncached_count`
  - Gemini: Special batching logic adjusted for uncached count
- Place cache control at calculated index
- Remaining messages after that index stay dynamic

**4. Response Processing (process() method)**
```
IF _responseFormat == "json":
    Use existing JSON extraction and parsing
    Extract fields from JSON structure
    
ELSE IF _responseFormat == "simple":
    NEW: Simple format parser
    - Regex pattern to find parenthetical groups
    - Extract based on enabled fields
    - Map by position to variables
    - Everything after = message text
    
Set same global variables regardless of path:
- $GLOBALS["HERIKA_PERS"]
- $GLOBALS["SCRIPTLINE_ANIMATION"]
- $GLOBALS["SCRIPTLINE_EXPRESSION"]
```

**5. Command Generation (processActions() method)**
- Should work unchanged
- Gets action/target from either JSON or simple parser
- Generates command strings same way
- Falls back to defaults when fields missing

## **Backward Compatibility**

**All defaults maintain current behavior:**
- `dialogue_cache_uncached_count: 4` (reasonable default)
- `response_format: "json"` (existing format)
- `include_actions_list: true` (existing behavior)
- `include_mood_requirement: true` (existing behavior)
- `include_target_requirement: true` (existing behavior)
- `include_listener_requirement: true` (existing behavior)

**Existing configurations:**
- Continue working without any changes
- Users can adopt new features incrementally
- No breaking changes to API or globals

## **Use Cases**

**Scenario 1: Maximum Quality for Simple Conversations**
```
response_format: "simple"
include_actions_list: false
include_mood_requirement: false
```
Result: LLM only outputs `(listener) message` - minimal cognitive load

**Scenario 2: Keep Actions but Simplify Format**
```
response_format: "simple"
include_actions_list: true
include_mood_requirement: true
```
Result: Natural parenthetical format with all features

**Scenario 3: Standard JSON but Reduce Info Overload**
```
response_format: "json"
include_actions_list: false
include_mood_requirement: false
```
Result: Smaller JSON template, no action list, simpler for LLM

**Scenario 4: Default (Current Behavior)**
```
All defaults
```
Result: Exactly like current connector, no changes

---

## **Technical Considerations**

**Parser Robustness:**
- Simple format parser should handle malformed responses gracefully
- Use defaults when expected patterns not found
- Log warnings but don't crash on parse failures

**Performance:**
- Simple format may actually improve LLM response time (less tokens to generate)
- Cache control improvements reduce redundant API calls
- Overall: Potential performance gains with quality improvements

**Debugging:**
- Log which format is being used
- Log which fields are enabled/disabled
- Log cache control placement calculations
- Continue existing cache performance logging

---

This comprehensive design allows CHIM users to fine-tune their connectors for optimal quality vs functionality trade-offs, addressing the core problem of LLM response degradation while maintaining full backward compatibility.
