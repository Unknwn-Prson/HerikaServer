## Fix #1: Profile Section Settings Not Saving (CRITICAL)

### Problem

When editing connector settings in the **Profiles** section (not Main LLM Connectors), changes were not saved to the database. Settings like response format, caching options, and all other connector metadata were silently discarded.

### Root Cause

The Profiles page uses a special metadata merge system that looks for fields named `meta_vis[...]` to merge with the JSON metadata editor. However, the connector settings section was using `metadata[...]` naming convention, so the consolidation() JavaScript function ignored these fields entirely.

### Solution

Changed all connector setting field names in the Profiles section from `metadata[...]` to `meta_vis[...]`:

**Files Modified**:
- `ui/core/llm_connectors.php` lines 429-494 (Profiles section only)

**Changed Fields** (13 fields total):
- `provider_caching`
- `dialogue_cache_uncached_count`
- `minimize_quality_prompt`
- `response_format`
- `include_mood_requirement`
- `include_listener_requirement`
- `include_actions_list`
- `include_target_requirement`
- `max_dialogue_cache`
- `custom_system_instruction`
- `custom_last_instruction`
- `verbose_logging`

**Example**:
```html
<!-- OLD (didn't save) -->
<select name="metadata[response_format]" id="response_format">

<!-- NEW (saves correctly) -->
<select name="meta_vis[response_format]" id="response_format">
```

### Impact

**Before**: Profile section connector settings were completely non-functional - changes would appear to save but were lost on page reload.

**After**: Profile section connector settings now save correctly and persist between sessions.

**Note**: Main LLM Connectors section was NOT affected - it already worked correctly and uses different save mechanism.

## Fix #2: Simple Format Responses Not Appearing (CRITICAL)

### Problem

When using Simple format (instead of JSON), LLM responses were received from the API but never appeared in-game or were added to dialogue context. The text was completely lost.

This affected **both v1.0.19f and v1.1.2** - it was a pre-existing bug that was never caught because simple format mode was rarely tested.

### Root Causes

Three separate issues caused simple format to fail:

**Issue 1: No Fallback Handling**
- When `extractSimpleFormatFromBuffer()` returned `['found' => false]`, code fell through and returned empty string
- **Result**: Complete message loss when LLM didn't follow format exactly

**Issue 2: Regex Required Both Parentheses**
- Pattern: `\(([^)]+)\)` required BOTH opening and closing parentheses
- When using prefill `(` + LLM outputs `mood)` → Result: `(mood)` ✓ Works
- When LLM outputs full `(mood)` → Result: `((mood)` ✗ Fails
- **Result**: Prefill case failed unpredictably depending on LLM behavior

**Issue 3: Regex Didn't Handle Colons**
- Some LLMs output format markers with colon: `(mood): Hello there`
- Pattern didn't account for optional colon after format markers
- **Result**: Parsing failed when LLM added colons

### Solutions

These are legitimate fixes cherry-picked from v1.0.20-v1.0.22 (which had other problems but these fixes were correct):

**Solution 1: Add Fallback Handling (from v1.0.20 Bug #6)**

Added else block in connector when `$parsed['found']` is false:
```php
} else {
    // BUG FIX (v1.0.20): Simple format parsing failed - use fallback
    logMessage("ERROR: Simple format parsing failed! Using raw buffer as fallback.");
    logMessage("Buffer content (first 200 chars): " . substr($this->_buffer, 0, 200));

    // Mark as parsed to prevent re-parsing
    $this->_simpleFormatParsed = true;
    $this->_simpleFormatMessageStart = 0;
    $this->_lastReturnedLength = strlen($this->_buffer);

    // Return entire buffer (strip prefill if used)
    $bufferToReturn = $this->_usedPrefill ? substr($this->_buffer, strlen($this->_prefillContent)) : $this->_buffer;
    return stripReasoningTokens($bufferToReturn);
}
```

**Solution 2: Make Opening Parenthesis Optional (from v1.0.22 Bug #8)**

Changed regex pattern in `extractSimpleFormatFromBuffer()`:
```php
// OLD
$groupPattern = str_repeat('\(([^)]+)\)', $groupCount);

// NEW (opening parenthesis optional)
$groupPattern = str_repeat('\(?([^)]+)\)', $groupCount);
```

**Solution 3: Make Colon Optional (from v1.0.20 Bug #6)**

Updated pattern to handle optional colon:
```php
// OLD
$pattern = '/^\s*' . $groupPattern . '\s*(.*)$/s';

// NEW (optional colon after format markers)
$pattern = '/^\s*' . $groupPattern . '\s*:?\s*(.*)$/s';
```

### Files Modified

- `connector/openrouterjsoncached.php` lines 1035-1049 (fallback handling)
- `connector/openrouterjsoncached_verbose.php` lines 1720-1742 (fallback handling with verbose logs)
- `connector/openrouterjsoncached_helpers.php` lines 540-545 (regex pattern fixes)

### Impact

**Before**: Simple format completely non-functional - responses lost entirely.

**After**: Simple format now works correctly with:
- Format variations: `(mood)`, `mood)`, `(mood):`, `mood):`
- Fallback when LLM doesn't follow format instructions
- Proper logging for debugging

**Note**: These fixes were present in v1.0.20-v1.0.22 but lost when we reverted to v1.0.19f baseline due to other problems in those versions.

## Known Limitations

### Current

- Fallback mode returns raw buffer without format parsing - mood/action/listener not extracted
- Some LLMs may still produce format that fails both parsing and fallback (extremely rare)

### Future Considerations

- Add more lenient parsing patterns for common variations
- Improve fallback to attempt basic format extraction
- Add UI warnings when simple format fallback is frequently triggered
